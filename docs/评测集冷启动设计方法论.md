## 1. 先把问题定义清楚

两类Agent 的评测集来源根本不同：

| 前提 | 有历史用户数据 | 无历史用户数据（当前画布 Agent） |
| --- | --- | --- |
| 用户任务分布 | 已知，可统计 | 未知 |
| 用户表达方式 | 已知，可抽样 | 未知 |
| 失败样本 | 已积累（工单、转人工记录） | 无用户侧样本 |
| 评测集构造 | 从真实分布**抽样** | 从规范与风险**推导** |
| 代表性论证 | 外部效度：样本≈总体 | **不能用同一套论证** |

结论很直接：**没有用户数据时，「分布代表性」是不可证明的，继续追求它只会得到自我安慰式的结论。** 在报告里宣称「该评测集代表真实用户」属于越界表述。

替代方案不是降低要求，而是换成三条**可验证**的性质：

1. **构造完备性**：是否覆盖了「能力 × 状态 × 风险 × 已知失败模式」的规范空间，可脚本核算；
2. **判别力**：能否区分好坏版本、能否抓住人为注入的缺陷，可实验测量；
3. **可演进性**：一旦拿到真实分布，能否只重算权重、补覆盖缺口，而不推翻既有资产。

即：

\[
\text{评测集价值} = \text{覆盖完备性} \times \text{判别力} \times \text{可演进性}
\]

「像真实用户」在冷启动期是不可测的，不作为验收目标。

## 3. 抽样框：把「拍脑袋 50 条」换成可辩护的配额

当前 50 条的分配依据只有方法论 5.1 的场景占比表（触发 12% / 核心 56% / 产物 16% / 异常 16%），这解释了「场景比例」，但没解释**同一场景内为什么是这些用例**。建议显式定义抽样框（sampling frame）。

### 3.1 维度定义

| 维度 | 取值来源 | 说明 |
| --- | --- | --- |
| 意图 intent | 10 个行为类别 | 读 / 建 / 改 / 删 / 连 / 编排 / 生成 / 批量 / 布局 /澄清 |
| 对象 object | 节点类型 15 种 + 连线 + 视口 + 选区 | 决定协议字段复杂度 |
| 前置状态 precondition | 空白/ 单节点 / 多节点带连线 / story 已有运行态结构 / 含被拒历史 | 当前 50 条**全部从空白开始**（口径声明），是已知缺口 |
| 表达 phrasing | 明确 / 口语 / 省略指代 / 一句多意图 / 粘贴长文 | 见第 5 节 |
| 样本类型 | 正/ 负 / 边界 / 对抗 | 方法论 5.2 |
| 风险 | P0 / P1 / P2 | 契约 `categories.riskLevel` + 门禁 |
| Agent 变体 | echo / codex / hermes | 契约 `agentVariants` 已定义差异（Echo 4 步上限、插件节点提示词覆盖差异） |

### 3.2 配额权重公式

无用户数据时，用三个可辩护代理替代「频次」：

\[
P(\text{cell}) = 0.5 \cdot \text{Impact} + 0.3 \cdot \text{Fragility} + 0.2 \cdot \text{Reachability}
\]

| 因子 | 打分依据（0–3） |
| --- | --- |
| Impact 影响度 | 不可逆性（删除 / 覆盖）、越界与安全、真实性（虚报完成）、状态污染 |
| Fragility 脆弱性 | 历史缺陷条数、涉及归一化点数量、必填协议字段数（`kind` / `outcomeId` / `patch.type`） |
| Reachability 可及性 | 是否产品主叙事路径、UI 入口深度、是否被Agent Prompt 显式声明 |

配额：\(n_{\text{cell}} = \operatorname{round}\left(N \cdot P_{\text{cell}} / \sum P\right)\)，并设下限：**每条 `rejectionReasons`、每条 `failureModes`、每条 `highRiskPaths` 至少 1 条用例**；P0 类别至少 3 条且含 1 条对抗例。

这样「为什么是这些用例」有可复核的推导，而不是个人偏好。

## 4. 五层评测集架构

当前 50 条是以自然语言任务驱动的 L1 主体，其中已人工挑选覆盖多项 L0 协议规则和 L3 对抗风险；L2 基本空缺，L4 证据薄弱。真正尚缺的是**从 Schema 自动派生、以组合覆盖证明完备性**的独立 L0 层，而不是“完全没有协议测试”。

| 层 | 名称 | 规模量级 | 生成方式 | 判据 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| **L0** | 协议一致性 | 数百 | **自动生成**（枚举 + pairwise） | 纯确定性规则 | 已有人工挑选的关键样本；缺自动派生的组合覆盖层 |
| **L1** | 能力单元 | 100–200 | 专家设计 | 规则 + Rubric | 已有 50 条主体 |
| **L2** | 端到端工作流 | 15–30 | 专家设计（多轮长链路） | 规则 + Judge + 人工 | 缺失（最大用户价值缺口） |
| **L3** | 对抗与安全 | 30–50 | 红队设计 + LLM 扩展 | 规则优先 | 已有 7 条对抗例，尚未形成独立池 |
| **L4** | 创意与主观质量 | 20–40 | 专家设计 | Judge + 人工，多样本 | 极弱（生成类无可读产物） |

### 4.1 L0：用组合覆盖换取廉价的完备性

从schema 直接派生，**不需要为每条手写期望**：

- 输入维度：工具（23）× 画布类型（2）× 节点类型（15）× 参数边界（缺 id / 不存在 id / 空 metadata / 超长文本 / 非法枚举值）；
- 不做全笛卡尔积（爆炸），采用 **pairwise（2-way）覆盖**，把上万组合压到数百条；
- 期望由规范推导：例如「content 画布 + story-only 节点类型 → 必然命中 `node-type-canvas-mismatch` 且必须被转述」；
- 价值：一次性把 6 条 rejection、4 条归一化、15 种节点类型全部压到有断言覆盖，成本远低于人工设计。

L0 不评语义质量，只保证协议层不出现「静默失败」「越界写入」「不转述拒绝」。

### 4.2 L2：真正接近用户价值的一层

L1 测「单个能力对不对」，L2 测「一个真实创作任务能不能被完成」。示例：

- 「我有一个末世剧情的想法，帮我在编排画布里搭出3 章、每章 2 个分支，最后有 2 个结局」→ 10+ 步、跨轮上下文、`kind`/`outcomeId` 全对、可达性无死路；
- 「把这段 800 字大纲拆成分镜文本节点，并给每个镜头挂一个生图配置」→ 长文本解析 + 批量 + 连线血缘；
- 「刚才那批里第3 个不对，重做它，别动别的」→ 指代消解 + 局部修改 + 无副作用。

L2 的判据不能只看单步工具，而要看：任务完成度、状态污染、是否需要用户返工、是否如实交代未完成项。**这一层最难自动化，也最不可替代。**

## 5. 表达分布：任务可以推导，说法只能模拟

任务分布可由规范推导，但**用户怎么说**无法推导。处理方式：

1. **结构先定，表达后生成**（契约 `sourcesPolicy.expanded` 已规定）：人工确定意图、前置状态、期望、判据；只让 LLM 生成自然语言表达。禁止 LLM 自行决定期望。
2. **Persona × 风格矩阵**：新手 / 熟练 / 急躁；口语化、省略主语、中英混杂、一句多意图、带错别字、粘贴大段大纲、直接下命令不给上下文。
3. **语义等价类**：同一意图保留 3–5 个表达变体，用于测**表达鲁棒性**（同一等价类结果应一致）。纪律：**同一等价类的所有变体必须落在同一个 split**，否则 Selection/Test 之间会发生泄漏。
4. **用户模拟器**：澄清能力（`clarification-degradation`，当前 5 条）只有在「Agent 提问 → 模拟用户回答 → 继续执行」的多轮交互下才能真正被测。当前 Runner 用预置多轮消息铺状态，无法响应 Agent 的追问，这是评测能力本身的缺口，而不是用例数量问题。

## 6. 如何客观证明评测集有价值（不依赖用户数据）

这是整套方案的关键，也是当前完全缺失的一环。四个可量化指标：

### 6.1 缺陷注入捕获率（核心指标）

方法：在 Agent 侧**有意注入已知缺陷**，跑评测集，看能否判失败。项目的 69 条历史缺陷是天然注入库。

| 注入变异 | 期望被捕获的用例 |
| --- | --- |
| 删除 Prompt 中「写操作前先`canvas_get_state`」 | 必需步骤 / 顺序类 |
| 删除 content/story 隔离段| EX-01、EX-02、TR-05 等 |
| 删除「必须显式传 `kind`」 | CL-17、CL-19、OQ-02 |
| 删除「不要编造执行结果」 | OQ-04、OQ-08、EX-06 |
| 删除「被拒后不要改建文本节点冒充」 | EX-03 |
| 关闭 `connection-dedupe` 的 `outcomeId` 判重 | CL-18 |
| 工具层不再返回 `rejections` | `REJECTION_REPORT_REQUIRED` 相关 |

**必须同时包含「良性变异」**（例如关闭 `reorder-add-node-first`，契约明确规定顺序错误但语义正确不判失败），用于测量**误杀率**。

指标：

- 缺陷捕获率 \(= \frac{\text{被至少一条用例判失败的注入数}}{\text{注入总数}}\)，P0 类目标 \(100\%\)；
- 误杀率 \(= \frac{\text{良性变异被判失败数}}{\text{良性变异数}}\)，目标 \(0\)。

工程前提：`canvas-agent/src/config.ts` 的 `AGENT_PROMPT` 目前是硬编码常量，无覆盖入口。需要为跑测侧增加 Prompt 变体注入能力（只作用于 Runner 的隔离 `codex-home`，不改产品默认行为），这项能力当前不存在，需要单独评估。

### 6.2 版本判别力

在多个被测配置（Echo vs CodeX、不同模型）上跑同一套用例：

- **非平凡用例占比** = 至少在两个配置上结果不同的用例比例；
- 在所有配置上恒 pass 或恒 fail 的用例信息量为 0：恒 pass 的降级为抽样集，恒 fail 的先确认是 Agent 缺陷还是用例/规则缺陷（本轮 CL-25就是后者）。

### 6.3 冗余度

结果向量完全一致的用例对视为冗余候选，按方法论第 14 节的防膨胀规则同簇保留代表例。这决定回归集能否长期维护。

### 6.4 规范覆盖率（可立即脚本化）

对照契约核算：6 条 `rejectionReasons`、9 条 `failureModes`、8 条 `highRiskPaths`、15 种节点类型、8 种 op、3 种连线 kind 各被多少条用例覆盖，输出缺口清单。**这项现在就能做，不需要新增任何跑测。**

## 7. 从冷启动到真实分布的演进

| 阶段 | 数据来源 | 评测集动作 | 可宣称的结论 |
| --- | --- | --- | --- |
| 阶段 0（当前） | 规范 + 缺陷史 | 规范驱动构造+ 注入实验 | 「覆盖了 X 条契约约束，捕获率 Y%」 |
| 阶段 1 | 团队 dogfooding 会话 | 按现有 Trace 结构落盘，每周抽样标注，回补覆盖缺口 | 「覆盖了团队真实使用中出现的 N 类任务」 |
| 阶段 2 | 内测 / 灰度 | 用真实分布**重算第 3 节权重**，不推翻用例 | 「按内测分布加权后的通过率」 |
| 阶段 3 | 上线流量 | 建 Online Replay split（方法论 5.3） | 此时才可谈**分布代表性** |

关键设计原则：**权重与用例解耦**。用例是资产，权重是可替换的参数。这样拿到真实数据时不需要重建评测集。

阶段 1 的成本最低、收益最高：团队每天都在用画布 Agent，这些会话现在没有被采集。

## 8. 已知局限与偏差（必须写进报告）

| 偏差 | 表现 | 缓解 |
| --- | --- | --- |
| **出题人偏差** | 写 Prompt 的人和出用例的人同源，会系统性避开自己没想到的失败 | 缺陷注入实验、独立红队（另一个模型/另一个人出题）、引用上游 `basketikun/infinite-canvas` 的 issue |
| **规范盲区** | 契约只写了「能力正确性」，没写「用户是否觉得好用」（返工次数、心智负担、审美） | L2 工作流层 + L4 主观质量层 + dogfooding 观察 |
| **覆盖 ≠ 价值** | 100% 协议覆盖仍可能做不好一个真实创作任务 | L0 与 L2 分开统计，禁止用 L0 通过率代表整体质量 |
| **单轮 N=1** | 当前无稳定性数据 | 按契约 P0×5 / P1×3 补跑 |
| **产物证据缺失** | 生成类无可读产物，`RUBRIC_CREATIVE_ALIGNMENT` 无法评| 先补 Trace 的generation/artifact 记录，再谈创意质量评分 |
