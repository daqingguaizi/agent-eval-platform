# Golden Set 评分工作台人工评分使用指南

> **适用范围**：Canvas Agent Golden Set 的人工评分、P0 双评与裁决。
> **当前基线**：`gs-full-1 / baseline-v1`，共 50 条、每条为 `N=1`。
> **唯一评分口径**：[`SCORING_STANDARD.md`](./SCORING_STANDARD.md)。本指南只说明平台操作流程；出现理解冲突时，始终以评分标准为准。

---

## 1. 先明确：人工评分在做什么

人工评分不是重新运行 Agent，也不是只看最终回复。评审人需要基于同一条 Trace，确认：

1. **实际发生了什么**：工具调用、参数、画布状态变化、执行层拒绝和最终输出；
2. **规则结论是否有充分证据**：确定性评分只判断结构化事实，不能凭印象推翻 Trace 已确认的事实；
3. **语义质量是否合格**：回复是否如实、是否真正解决任务、是否清晰可执行、生成类结果是否贴合要求；
4. **Case 最终结论**：通过、失败，或证据不足时转人工复核；
5. **后续处置**：是否进入 Badcase、Regression 或 Judge Calibration。

`Runner 执行完成` 只说明跑测器运行正常，**不代表 Case 已通过质量评测**。`LLM Judge 尚未运行` 也不等于通过或失败；首轮 50 条均必须提交人工评分。

### 1.1 Hard Gate 是什么：评审前 30 秒说明

**Hard Gate 是当前 Case 中某一条 Rule 的“硬约束”标记，不是 P0/P1/P2 风险等级，也不是上线发布开关。** 只有同时满足以下两项，才是 Hard Gate 失败：

1. 该 Rule 在当前 Case 的评分配置中标为 `hardGate=true`；
2. 该 Rule 的结构化证据结果为 `fail`。

| 容易混淆的概念 | 它回答的问题 | 评审时怎么用 |
| --- | --- | --- |
| `P0 / P1 / P2` 风险等级 | 这条 Case 出问题的影响有多大？ | P0 必须双评；它不等于“所有 Rule 都是 Hard Gate”。P1/P2 也可能有 Hard Gate。 |
| Hard Gate | 这条具体 Rule 能否被诊断分或 Rubric 抵消？ | 不能。已证实的 Hard Gate 失败使该 Case 判为 `fail`。 |
| 发布门禁 | 某个版本能否上线？ | 当前 Golden Set Runner 不执行发布阻断或回滚；这里只产出 Case 级认证证据。 |

工作台的 **Hard Gate 数量** 表示当前 Case 有多少条被标为硬约束的 Rule，并不表示已经失败。请在“确定性评分”中查看每条带 `Hard Gate` 标签的 Rule 状态：

- `pass`：这条硬约束已满足；
- `fail`：确认 Trace 事实后，Case 必须选“失败”；不能用高 Rubric 分抵消；
- `not_applicable`：该 Rule 不适用于这条 Trace，不是失败；
- `needs_human_review` / `evidence_invalid`：证据不足、冲突或评分证据损坏，不是“自动 Hard Gate 失败”；按实际情况转待复核并说明原因。

右侧“我已核对适用 Hard Gate 的事实”只是确认你已检查相关 Rule，并不代表该 Case 一定有 Gate 失败。若认为 Rule 的事实判断有误，不能直接凭感觉改判通过；应引用冲突证据并提交“待进一步复核”或进入裁决。

## 2. 角色与分工

| 角色 | 可做什么 | 何时使用 |
| --- | --- | --- |
| 评审人 A（`reviewer_a`） | 完成第一份人工评分 | 所有 Case 至少一份；P0 必须有 A。 |
| 评审人 B（`reviewer_b`） | 完成第二份评分 | 所有 P0；以及低置信、生成争议、规则/Judge 冲突或 `needs_human_review` 的 P1/P2。 |
| 裁决人（`adjudicator`） | 对冲突给出最终结论 | 双评 verdict、Hard Gate 或任一关键 Rubric 相差 ≥2 分时。 |
| 评测协调人 | 分配 Case、检查完成率、维护评审批次 | 不替代评审人的证据判断。 |

### 2.1 P0 双评纪律

P0 必须有 A、B 两个角色的独立评分提交。当前处于单人评测阶段，**同一人可分别以 `reviewer_a` 和 `reviewer_b` 完成两次评分，`reviewerId` 是否不同不作为双评完成条件**。两次评分仍应基于 Trace、规则与证据卡分别判断；建议 B 提交前不查看 A 的结论。当前工作台会展示历史记录，因此该过程由评审流程自律保证。

## 3. 评分前准备

### 3.1 仅需由协调人执行一次

在工作台目录启动本机 Review 服务：

```bash
cd /Users/wyneefan/CodeBuddy/echo-infinite-canvas-main-7.27/agent-eval-platform/golden-set-runner
npm run review-workbench
```

浏览器打开：`http://127.0.0.1:8765/viewer/index.html`。

页面顶部必须显示 **`Review 模式 · 可保存`**。若显示“只读模式”，说明当前仅通过静态服务器打开，能浏览但不能保存人工评分；请停止静态服务后改用上述命令。

> 服务只监听 `127.0.0.1`，评分记录写入 `assessments/<runId>/<assessmentId>/reviews/`。评审人无需也不应手工编辑 JSON。

### 3.2 每位评审人开始前检查

1. 确认 Run 为 `gs-full-1`、Assessment 为 `baseline-v1`；如页面字段不同，填入对应批次后点击“加载”。
2. 先阅读 `SCORING_STANDARD.md` 的第 4、5、7、8、9 节：Verdict、证据、Rubric、Hard Gate 与裁决要求。
3. 在左侧列表中按风险、场景、最终结论、人工状态筛选自己被分配的 Case。
4. 优先处理：P0、`Hard` 标记、`待人工`、生成类、规则与 Judge 结论冲突项。

## 4. 单条 Case 的标准评分步骤

对每一条分配到的 Case，严格按以下顺序操作；不要跳过 Trace 直接给分。

### 步骤 1：打开 Case 并理解评测目标

1. 在左侧点击 Case ID。
2. 在 **“概览”** 核对风险等级、场景、画布类型、最终画布状态、确定性结论、Hard Gate 数量和诊断分。
3. 注意：页面的“最终结论”是当前 assessment 结论或规则候选，不是要求你照抄的人工结论。

### 步骤 2：检查原始 Trace 事实

切换到 **“Trace 证据”**，按被测轮依次检查：

1. 用户消息是否与 Case 任务一致；
2. 工具调用、参数和真实 `ops` 是否满足任务；
3. `diff`、执行后状态和 `finalState` 是否证明预期状态真的发生；
4. 是否出现执行层拒绝（红色“执行层拒绝”）、错误、未处理失败或不应出现的状态变更；
5. 最终输出是否忠实描述已完成、未完成和被拒绝的内容；
6. 生成类 Case 还要检查生成记录、产物路径/错误和节点生成状态。

**取证原则**：工具、状态、diff 和 rejection 是一级事实证据；最终回复只是语义证据，不能推翻已确认的执行事实。

### 步骤 3：复核确定性评分

切换到 **“确定性评分”**：

1. 展开所有 `fail`、所有 `Hard Gate` 和与你结论相关的规则；
2. 阅读每条规则的“期望”“实际”“问题类型”和“理由”；
3. 点击“证据”按钮，工作台会跳回对应的 Trace 位置；
4. 判断该规则证据是否完整、规则是否适用；若发现归一 Trace 与 Raw Event 冲突，标记 `evidence_invalid` 或在理由中说明，不能主观猜测；
5. **适用 Hard Gate 失败不能被 Rubric 高分抵消**。对其复核事实后，Case 应为 `fail`，或证据损坏时转 `needs_human_review`。

### 步骤 4：查看 Judge 作为语义辅助

切换到 **“LLM Judge”**：

- Judge 已完成时，查看每个 Rubric 的 `0–4` 分、置信度、理由、证据按钮和完整 JSON；
- Judge 未完成、低置信、解析异常或证据无效时，必须由人工独立判断；
- Judge 只能提供语义建议，**不能推翻**工具、状态、rejection 等一级事实，也不能替代人工首轮金标。

### 步骤 5：按“三段式”填写右侧“人工评分”

页面不再要求输入 JSON Pointer。每一段都用业务语言展示，但提交后仍会由系统保存结构化证据和治理标签。

#### 第一段：判断结果

1. 填评审人；首评选“评审人 A”，P0 第二位评审选“评审人 B”，裁决时选“裁决人”。
2. 选择 Case Verdict：
   - **通过**：关键要求已满足；
   - **失败**：Hard Gate 或质量要求未满足；
   - **待进一步复核**：证据不足、冲突或无法公平判断。
3. 有适用 Hard Gate 时，先核对页面提示的事实；证据不足时选“待进一步复核”，不要猜测。
4. 每个适用 Rubric 直接在中文判分卡中选择最符合证据的一档。卡片展开后可看到 `0–4` 每一分的条件、优先核对的证据和边界说明。

完整逐分解释见 [`人工评分判分卡.md`](./人工评分判分卡.md)。它是 `SCORING_STANDARD.md v1.0.0` 的操作说明，不改变评分标准或现有 `baseline-v1`。

#### 第二段：评分依据

1. 勾选至少一张支持本次结论的**关键证据卡**，例如“关键工具操作”“画布状态变化”“执行层拒绝”“最终回复”。
2. 点击“查看 Trace”可跳到原始时间线对应位置；不需要理解或手填 `/turns/...` 路径。
3. 填写简短评分说明：通过时可选；失败、待复核或与系统事实不一致时必须说明“事实 → 结论”。

例如：

```text
执行层已拒绝 story-choice 操作，最终画布也没有产生该节点；
但最终回复仍称“全部完成”。因此事实是否如实说明为 0 分，Case 判为失败。
```

#### 第三段：问题与后续用途

这些字段仍是日常评分的一部分，用于后续治理，但不要求理解内部标签：

| 页面提问 | 如何选择 |
| --- | --- |
| **发生了什么问题？** | 选择最直接观察到的现象，如“回复把事实说错了”“关键操作没有执行”“画布最终状态不正确”。没有问题或暂时无法确定时选第一项。 |
| **优先排查哪个环节？** | 选择“理解任务与上下文”“制定执行步骤”“选择或调用工具”“执行层与画布状态”“回复表达”“评测规则或数据”等一个或多个方向。这是排查建议，不是最终归责。 |
| **记录为问题样本** | 已确认存在质量问题，后续值得分析修复时选择。 |
| **加入防回退检查** | 修复后应反复复测；P0、Hard Gate 和典型失败优先选择。 |
| **作为评分对照样本** | 人工结论清晰且具有代表性，未来可用于 Judge 校准时选择。 |

系统会给出建议及理由；评审人可根据 Trace 调整，也可选择“没有问题 / 暂不标记”。

### 步骤 6：先保存草稿，再正式提交

1. 填写时系统会自动保存草稿；关键修改后仍建议点击 **“保存草稿”**。
2. 在提交前再次检查：评审人、角色、Verdict、所有适用 Rubric、Hard Gate 事实确认、至少一张关键证据卡和必要理由。
3. 点击 **“提交评分”**。提交后该记录进入审计历史，不应再通过手工修改文件改写。
4. 刷新页面并在“人工评分”页签确认你的记录、时间和证据链接均可见。

提交至少需要：评审人、有效角色、Case verdict、至少一个 Rubric 分数、至少一张关键证据卡和评分理由。流程要求高于系统最小校验：请始终填写所有适用 Rubric，并逐条复核带 `Hard Gate` 标签的 Rule。

## 5. P0 双评与裁决操作

### 5.1 P0 双评

1. 用 `reviewer_a` 完成第一份评分并提交；列表会显示“待双评”。
2. 用 `reviewer_b` 完成同一 Case 的第二份评分并提交。单人评测阶段可填写与 A 相同的 `reviewerId`，但应作为一次新的、基于证据的评分提交。
3. 两份评分的 Verdict、Hard Gate 和关键 Rubric 均一致时，P0 双评完成；工作台可能显示“已裁决/已完成”，这表示双评结论已闭环，不要求额外人工裁决记录。
4. 若 Verdict 不同、Hard Gate 判断不同，或任一关键 Rubric 相差 `≥2` 分，必须进入裁决。

### 5.2 裁决

1. 裁决人打开同一 Case，先查看“人工评分”历史、“确定性评分”“LLM Judge”“Trace 证据”和“裁决与 Badcase”。
2. 在右侧表单将角色选为 `adjudicator`，填写最终 Verdict、适用 Rubric、Hard Gate、证据引用和理由。
3. 理由必须明确说明采纳哪份证据、为何接受/拒绝前序结论；不能只写“同意 A”或“同意 B”。
4. 点击 **“裁决提交”**，确认“裁决与 Badcase”中最终结论和审计历史已更新。

## 6. 评分完成后的协作动作

每个评审批次结束后，协调人应在工作台仪表盘和列表中检查：

1. 人工进度是否达到 `50 / 50`；
2. 所有 P0 是否都有 A、B 两份独立提交；
3. 是否仍存在 `待人工`、`待双评`、低置信或冲突 Case；
4. 所有确认失败是否填写了问题类型、责任模块和 Badcase/Regression 建议；
5. 是否已为 Judge Calibration 保留代表性人工金标（明确通过、明确失败、边界、拒绝/部分成功和生成类）。

首轮基线只有在上述项目完成后才可称为“人工认证基线”。它仍是 `N=1`，不能据此宣称稳定性、`pass@k`、`pass^k` 或发布安全性已被证明。

## 7. 常见问题

| 现象 | 处理方式 |
| --- | --- |
| 页面显示“只读模式” | 用 `npm run review-workbench` 启动，访问 `127.0.0.1:8765`，不要用 `python3 -m http.server` 做正式评分。 |
| 保存失败 | 检查 Review 模式、Run/Assessment 名称、评审人、Rubric、证据引用和评分标准版本；不要直接修改 assessment 文件。 |
| 不知道选择哪条证据 | 先选工作台推荐的关键证据卡；点击“查看 Trace”可跳到工具步骤、拒绝、状态变化或最终回复。只有这些证据不足时，才从 Trace 时间线补选。 |
| 规则评分与个人判断不同 | 先检查 Trace/Raw 是否冲突；结构化事实以证据为准，语义分歧写入人工理由；必要时提交 `needs_human_review` 并触发双评/裁决。 |
| Judge 没有结果 | 这是正常状态，首轮人工评分照常进行；Judge 需人工金标校准后才可运行。 |
| P0 已有 A 的结果，B 怎么保证独立 | 协调人先分配；B 在提交前不查看人工历史和裁决结论，只依据 Trace、规则与 Judge 证据评分。 |
| 需要离线交接评分 | 使用“导出评分包/导入评分包”；导入会校验 Trace 和评分标准哈希，不匹配的包不能导入。 |

## 8. 禁止事项

- 不要仅根据最终回复、Runner `ok` 或 Judge 单一结论评分；
- 不要用高 Rubric 分抵消 Hard Gate 失败；
- 不要把 `maxTokens` 超限直接判为失败：`gs-full-1` 当前为 `observe_only`；
- 不要把 `needs_human_review` 强行算作通过或失败；
- 不要编辑 `runs/gs-full-1/` 的历史 Trace，也不要手工改写已提交评分；
- 不要用已被优化过程反复查看的 50 条基线，单独宣称新版本已验收通过；后续仍须使用独立 Selection/Test 集。
