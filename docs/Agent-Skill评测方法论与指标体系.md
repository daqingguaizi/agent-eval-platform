# Agent / Skill 评测方法论与指标体系

> **版本**：v1.0  
> **整理日期**：2026-07-28  
> **适用对象**：对话 Agent、知识问答 Agent、工具执行 Agent、诊断决策 Agent、代码 Agent，以及被 Agent 调用的 Skill  
> **目标**：建立一套可重复、可量化、可归因、可回归、可持续优化的质量工程体系

---

## 0. 文档摘要

Agent / Skill 评测不是上线前抽查几条 Case，也不是只检查最终回答是否“看起来正确”，而是将非确定性的智能行为持续收敛为可发布、可运营的工程质量。

一套完整的评测体系需要形成以下闭环：

```text
定义质量契约
    ↓
建设评测数据资产
    ↓
执行 Agent 并采集结构化 Trace
    ↓
确定性评分 + LLM-as-Judge + 人工复核
    ↓
Badcase 分析与根因定位
    ↓
受控修改 Prompt / Skill / 工具 / 知识
    ↓
独立验证集门控与发布判断
    ↓
线上灰度、监控、反馈回流
    └────────────────────→ 回到评测资产
```

核心原则可以浓缩为八句话：

1. **先定义成功和风险，再设计指标。**
2. **结果与过程必须同时评测。**
3. **能用代码判断的，不交给模型判断。**
4. **平均分不能掩盖 P0 风险。**
5. **同一个任务必须多次运行，区分能力上限与生产稳定性。**
6. **Badcase 必须定位到责任模块和可执行修复动作。**
7. **Skill 优化必须小步修改，并由独立验证集决定是否接受。**
8. **评测终点不是报告，而是可复用的质量资产与发布决策。**

## 2. 为什么传统测试方法不够

### 2.1 Agent 的三类本质难题

#### 非确定性

同一输入、同一模型、同一 Prompt，多次执行也可能产生不同规划、工具调用和最终回答。因此，单次跑通只能证明“曾经成功”，不能证明“稳定可用”。

#### 黑盒化

模型、Prompt、Skill、知识库、工具 Schema 或外部依赖的微小变化，都可能改变 Agent 行为。只观察最终答案，很难判断变化发生在哪个环节。

#### 错误级联放大

Agent 往往经过意图理解、计划、检索、工具调用、结果解释和回复生成等多步链路。前序环节的小错误可能在后续被放大为错误结论、错误操作甚至资损和合规事故。

### 2.2 只看最终答案的风险

最终答案正确不等于过程正确。例如：

- 没有调用必要工具，却依据模型记忆碰巧答对；
- 工具参数错误，但外部系统返回了看似合理的数据；
- 最终回复合规，但中间 Trace 已泄露敏感信息；
- 结果正确，但执行了越权写操作；
- 结论正确，但成本和延迟是基线的数倍。

这类样本属于**结果假阳性**。生产评测必须同时检查 Outcome、Output 和 Trace。

## 3. 评测总框架

## 3.1 六个核心问题

一套成熟评测体系至少回答：

| 问题 | 对应模块 |
|---|---|
| Agent / Skill 是否完成了任务？ | 功能正确性、Outcome 评测 |
| 最终回复或产物是否准确可用？ | Output 质量评测 |
| 执行过程是否合规、合理、可复现？ | Trace 过程评测 |
| 多次运行是否稳定，成本是否可接受？ | 鲁棒性、效率成本评测 |
| 失败发生在哪里，应该由谁修？ | Badcase RCA |
| 新版本是否值得接受和发布？ | 验证门控、发布门禁、线上灰度 |

## 3.2 五层观测模型

### Turn 层

评估单轮回复：事实、语义、指令遵循、表达和安全。

### Session 层

评估整段会话是否最终解决问题，是否发生目标漂移、上下文丢失、重复追问、无效循环或错误升级。

### Output 层

评估最终文本、文件、代码、报告、图表、数据库状态等产物。

### Trace 层

评估路由、计划、检索、工具、参数、顺序、重试、状态变化、异常处理和证据使用。

### Outcome / System 层

评估真实任务结果、用户行为、业务效果、系统延迟、Token、成本和可用性。

> 对话 Agent 不应简单平均每轮得分。即使每一轮都“基本合理”，整段会话没有解决用户问题，仍应判失败。

## 4. 第一步：定义质量契约

评测前应先明确质量契约，避免评测后再临时解释指标。

## 4.1 识别 Agent / Skill 类型

| 类型 | 主要风险 | 评测侧重点 |
|---|---|---|
| 知识问答型 | 事实错误、幻觉、引用不实 | 答案正确性、证据忠实性、引用溯源 |
| 多轮对话型 | 上下文丢失、目标漂移、未解决问题 | Session 成功率、澄清能力、转人工策略 |
| 工具执行型 | 工具选错、参数错误、状态污染 | 路由、调用顺序、参数、状态变更、幂等性 |
| 诊断决策型 | 根因误判、错误建议、过度承诺 | 根因准确性、必要证据、风险边界、稳定性 |
| 代码 Agent | 代码不可运行、破坏原功能、安全漏洞 | 编译、测试、静态检查、改动范围、回归 |
| 创意生成型 | 风格不符、内容不可用 | 约束满足、可用性、偏好和多样性 |

## 4.2 确定风险等级

建议把指标分为三级：

- **P0：上线门禁。** 安全、合规、资损、越权、关键事实和关键动作。失败即拒绝发布。
- **P1：版本比较与工程优化。** 过程、稳定性、效率、主要产物质量。
- **P2：体验与长期观察。** 风格、清晰度、同理心、满意度和业务趋势。

## 4.3 定义成功标准

每个任务至少要定义：

1. 必须完成的最终结果；
2. 必须执行的关键步骤；
3. 允许存在的等价路径；
4. 禁止执行的动作；
5. 必须使用的证据；
6. 输出格式和必填字段；
7. 异常时的降级行为；
8. 延迟、Token、工具次数和成本边界。

## 5. 第二步：建设评测数据资产

## 5.1 四场景用例法

| 场景 | 要回答的问题 | 典型检查 | 建议占比 |
|---|---|---|---:|
| 触发与路由 | 该不该触发？触发哪个 Skill？ | 正向触发、表达变体、误触发、漏触发 | 10%–15% |
| 核心逻辑 | 触发后过程是否正确？ | 分支、工具、参数、顺序、证据、状态变化 | 50%–60% |
| 产物质量 | 最终产物是否准确可用？ | 结论、完整性、具体性、格式、可执行性 | 15%–20% |
| 异常容错 | 出错时能否稳住？ | 非法输入、缺字段、超时、工具失败、攻击 | 15%–20% |

核心逻辑用例应覆盖全部关键分支，数量通常应为其他场景之和的 2–3 倍。

## 5.2 每类场景都要有四种样本

- **正例**：应触发、应成功完成；
- **负例**：不应触发、不应执行某动作；
- **边界例**：临界值、空数据、最大长度、状态组合；
- **对抗例**：Prompt Injection、越权诱导、敏感信息套取、恶意参数。

## 5.3 评测集分层

| 数据集 | 作用 | 是否参与优化 | 维护原则 |
|---|---|---:|---|
| Train / Capability | 暴露能力缺口，产生修改建议 | 是 | 主动扩展、允许低通过率起步 |
| Selection / Validation | 决定候选修改是否接受 | 否 | 独立、稳定、限制查询频次 |
| Test | 最终报告泛化能力 | 否 | 训练期间不可查看 |
| Regression | 防止已有能力回退 | 否 | 高风险样本长期保留 |
| Calibration | 校准 LLM Judge | 否 | 人工金标、覆盖边界和争议样本 |
| Online Replay | 重放真实线上分布 | 否 | 脱敏、版本化、定期更新 |

SkillOpt 的核心纪律是：训练集产生候选，独立 Selection 集决定是否接受，Test 只用于最终报告。

## 5.4 Golden Set 建设建议

早期先建设 **50–200 条高质量 Golden Set**，覆盖：

- 高频主路径；
- P0 风险路径；
- 历史 Badcase；
- 易混淆路由；
- 关键异常和降级；
- 典型对抗行为。

成熟后再扩展分类采样集、长尾集、对抗集和线上回流集。

## 5.5 推荐用例 Schema

```json
{
  "id": "case_001",
  "task_type": "tool_agent",
  "scenario": "core_logic",
  "risk": "P0",
  "input": {
    "question": "用户问题",
    "context": {},
    "fixture_refs": []
  },
  "expected": {
    "route": "target-skill",
    "outcome": {},
    "required_steps": [],
    "allowed_alternatives": [],
    "required_evidence": [],
    "forbidden_actions": [],
    "output_rubric": {},
    "max_latency_ms": 30000,
    "max_tool_calls": 8
  },
  "tags": ["high_risk", "regression"],
  "ground_truth_version": "2026-07-28"
}
```

## 5.6 数据漂移治理

如果用例依赖线上可变状态，每轮执行前应校验当前状态是否仍与建库时一致：

```text
状态一致 → 正常纳入统计
状态变化 → 标记漂移，不进入本轮分母
连续漂移 → 替换样本或改用 Fixture
```

Fixture、外部响应和知识快照应版本化，确保回归结果可复现。

## 6. 第三步：建立结构化 Trace

## 6.1 最低字段要求

每次运行至少记录：

- run_id、case_id、session_id、trace_id；
- Agent、Skill、Prompt、模型、工具和知识库版本；
- 用户输入及结构化上下文；
- 路由和计划结果；
- 检索 Query、召回文档、引用证据；
- 工具名称、参数、返回值、错误码；
- 状态变更前后值；
- 重试、超时和降级；
- 开始时间、结束时间、各阶段耗时；
- 输入/输出 Token 和估算成本；
- 最终回复或产物路径；
- Scorer 结果、置信度和判定依据。

## 6.2 Trace 示例

```json
{
  "case_id": "case_001",
  "run_id": "run_xxx",
  "versions": {
    "agent": "v1.8",
    "skill": "v2.3",
    "model": "model-a",
    "judge": "judge-b"
  },
  "trace": [
    {
      "step": 1,
      "type": "tool_call",
      "tool": "get_order",
      "args": {"order_id": "..."},
      "latency_ms": 320
    }
  ],
  "output": "最终回复",
  "usage": {
    "input_tokens": 1200,
    "output_tokens": 380,
    "tool_calls": 2,
    "latency_ms": 4600,
    "cost_cny": 0.08
  }
}
```

## 6.3 环境隔离

- 每个用例使用独立会话和状态空间；
- 写操作优先在 Sandbox 或 Mock 环境执行；
- 用例之间不得共享缓存、临时文件或数据库状态；
- 对非幂等动作使用回滚、事务或专用测试账号；
- 将原始 Trace、评分结果和版本信息统一归档。

## 7. 第四步：三类评分器分工

## 7.1 确定性评分器

负责所有可通过代码、断言或系统状态确定的事项：

- 是否调用必要工具；
- 是否选择正确工具；
- 参数和字段是否正确；
- 调用顺序是否符合关键约束；
- 文件、数据库和业务状态是否正确；
- 输出是否符合 JSON Schema；
- 是否出现禁止词、敏感信息和越权操作；
- 工具次数、Token、延迟和成本是否超标。

特点：快、便宜、稳定、可复现，应作为日常主力。

## 7.2 LLM-as-Judge

负责代码难以准确判断、但可通过结构化 Rubric 描述的事项：

- 语义和事实是否正确；
- 结论是否基于给定证据；
- 策略是否合理；
- 信息是否完整、具体；
- 建议是否可执行；
- 回答是否存在编造、过度承诺或答非所问；
- 整段 Session 是否解决问题。

### Judge 设计要求

1. 为每个分档提供可执行标准；
2. 输出结构化 JSON；
3. 输出 score、pass、reason、confidence 和 issue_type；
4. 提供正例、负例和边界 Few-shot；
5. 被测模型与 Judge 尽量使用不同模型或不同系列；
6. Judge Prompt 或模型变更后必须重新校准。

### Judge 推荐输出

```json
{
  "pass": false,
  "score": 0.55,
  "confidence": 0.86,
  "issue_type": "unsupported_claim",
  "reason": "回复给出了参考证据中不存在的具体承诺",
  "evidence": ["..."],
  "needs_human_review": true
}
```

## 7.3 人工评分器

人工主要承担：

- 建立业务 Ground Truth；
- 新评测集的前 20–50 个标杆答案；
- Judge 校准；
- 高风险样本终判；
- 规则与 Judge 冲突处理；
- 新模型、新 Prompt、新工具 Schema 的抽检；
- 低置信、边界和争议样本处理。

人工不适合长期承担全量日常评分。

## 7.4 评分路由

```text
第一层：规则粗筛
  ├─ 明确通过
  ├─ 明确失败
  └─ 存疑
       ↓
第二层：完整规则 + LLM Judge 精判
  ├─ 通过
  ├─ Badcase
  └─ 低置信 / 结论冲突
       ↓
第三层：人工终判
```

## 8. 第五步：完整指标体系

## 8.1 一级指标树

| 一级维度 | 回答的问题 | 优先级 |
|---|---|---:|
| 功能正确性 | 做对了吗？ | P0 |
| 鲁棒性与安全 | 靠谱吗，会不会翻车？ | P0 |
| 过程质量 | 过程合理、合规吗？ | P1 |
| 效率与成本 | 划算吗？ | P1 |
| 产物与体验 | 好用吗？ | P2 |
| 评测系统质量 | 评分本身可靠吗？ | 基础保障 |
| 线上业务效益 | 是否创造真实价值？ | 线上验证 |

## 8.2 功能正确性指标

| 指标 | 定义 | 推荐评分器 |
|---|---|---|
| 任务完成率 | 完成全部必要子目标的 Case 占比 | 规则 + Judge |
| 结果正确率 | 最终结论或状态与 Ground Truth 一致的比例 | 规则优先 |
| 路由准确率 | 正确选择 Agent / Skill / 工具链的比例 | 规则 |
| 工具选择正确率 | 调用工具集合符合要求的比例 | 规则 |
| 参数正确率 | 必填参数、取值和 Schema 均正确的调用占比 | 规则 |
| 状态变更正确率 | 写操作产生预期业务状态的比例 | 规则 |
| 指令遵循率 | 格式、约束、必填字段满足比例 | 规则 + Judge |
| 子目标完成度 | 已完成子目标数 / 应完成子目标数 | 规则 |

## 8.3 过程质量指标

| 指标 | 定义 | 推荐评分器 |
|---|---|---|
| 关键步骤覆盖率 | 已执行必要步骤 / 全部必要步骤 | 规则 |
| 工具序列合规率 | 调用顺序满足关键偏序约束的比例 | 规则 |
| 过程偏离度 | 实际路径相对参考约束的缺失、多余、乱序程度 | LCS / 图约束 |
| 证据充分率 | 结论有有效证据支持的比例 | 规则 + Judge |
| 证据忠实度 | 回复是否忠实使用证据而未篡改 | Judge |
| 上下文利用率 | 对有效上下文要点的覆盖程度 | Judge |
| 自纠错成功率 | 发生错误后识别并修复的次数 / 可纠错次数 | Trace 规则 |
| 澄清正确率 | 信息不足时正确询问而非猜测的比例 | Judge |
| 假阳性率 | 最终答案通过但过程检查失败的比例 | 规则 |

> 不应要求所有 Agent 严格复刻单一基线轨迹。应把过程要求拆成“必要步骤、禁止动作、偏序关系、允许等价路径”。

## 8.4 鲁棒性与安全指标

| 指标 | 定义 | 推荐评分器 |
|---|---|---|
| pass@k | 同一任务运行 k 次，至少一次成功的比例 | 重复执行 |
| pass^k | 同一任务运行 k 次，每次均成功的比例 | 重复执行 |
| 结果一致率 | 多次运行的核心结论一致程度 | 规则 + Judge |
| 异常恢复率 | 工具失败、超时或脏数据下成功降级的比例 | 故障注入 |
| 幻觉率 | 无依据事实、字段、承诺或引用出现比例 | 规则 + Judge |
| 敏感信息泄漏率 | 输出或 Trace 泄露敏感信息的比例 | 规则 |
| 越权率 | 执行超出授权范围动作的比例 | 权限断言 |
| 抗注入成功率 | 对抗输入下守住系统约束的比例 | 红队用例 |
| 漏拒率 | 应拒绝却执行的比例 | 规则 + 人工 |
| 误拒率 | 应执行却拒绝的比例 | Judge + 人工 |
| 死循环率 | 超出最大步骤或反复无效调用的比例 | Trace 规则 |

### pass@k 与 pass^k

对单个任务，若单次成功概率为 `p`，在近似独立时：

```text
pass@k = 1 - (1 - p)^k
pass^k = p^k
```

- pass@k 反映“多试几次能否成功”，适合观察能力上限；
- pass^k 反映“每次是否都成功”，适合生产可靠性。

关键决策、支付、退款、合规、诊断等场景应重点使用 pass^k。

## 8.5 效率与成本指标

| 指标 | 定义 |
|---|---|
| 端到端延迟 | 用户发起到最终结果返回的时间，报告 p50 / p95 / p99 |
| 模型延迟 | 各模型调用耗时 |
| 工具延迟 | 工具调用耗时及占比 |
| Token 消耗 | 输入、输出和总 Token，报告均值和 p95 |
| 工具调用次数 | 单任务平均和 p95 调用次数 |
| 重试率 | 重试调用数 / 总调用数 |
| 超时率 | 超时 Trial / 总 Trial |
| 单任务成本 | 模型、工具和基础设施成本之和 |
| 成功任务成本 | 总成本 / 成功任务数 |
| 成本增益比 | 指标提升量 / 新增成本 |

只看平均延迟容易掩盖长尾，必须至少报告 p95。

## 8.6 产物与体验指标

| 指标 | 定义 | 推荐评分器 |
|---|---|---|
| 要点覆盖率 | 已覆盖关键要点 / 应覆盖要点 | 规则 + Judge |
| 具体性 | 是否给出与当前问题匹配的具体原因和动作 | Judge |
| 可执行性 | 建议是否明确、可操作、无矛盾 | Judge |
| 格式合规率 | JSON、表格、文件、章节等格式是否正确 | 规则 |
| 清晰度 | 结构是否易读、表达是否明确 | Judge |
| 简洁度 | 是否存在明显冗余和重复 | Judge |
| 品牌风格一致性 | 是否符合产品语气和术语规范 | Judge |
| 主动澄清率 | 面对歧义是否提出必要问题 | Judge |
| Session 解决率 | 整段会话最终解决问题的比例 | Outcome + Judge |
| 重复追问率 | 用户因未解决而重复表达诉求的比例 | 线上日志 |
| 转人工率 | Agent 会话转人工比例 | 线上日志 |
| CSAT / NPS | 用户满意度和推荐意愿 | 用户反馈 |

## 8.7 Skill 专项指标

| 阶段 | 指标 |
|---|---|
| 触发 | Trigger Precision、Trigger Recall、误触发率、漏触发率 |
| 路由 | Skill 路由准确率、冲突 Skill 选择正确率 |
| 核心逻辑 | 分支覆盖率、关键步骤覆盖率、工具序列合规率 |
| 工具执行 | 工具选择正确率、参数 Schema 合规率、重试策略正确率 |
| 产物 | 目标完成率、具体原因命中率、格式合规率、可执行性 |
| 异常 | 降级成功率、错误信息准确率、状态污染率 |
| 迁移 | 跨模型保持率、跨 Harness 保持率、跨相近任务保持率 |
| 维护 | Skill 长度、规则冲突数、无效规则率、版本回归率 |

Trigger Precision / Recall：

```text
Trigger Precision = 正确触发次数 / 所有触发次数
Trigger Recall    = 正确触发次数 / 所有应触发次数
```

## 8.8 评测系统自身质量指标

评测器也可能出错，因此必须评测评测器：

| 指标 | 定义 |
|---|---|
| Judge 一致率 | Judge 与人工金标一致的比例 |
| Cohen's Kappa | 扣除随机一致后的 Judge 与人工一致性 |
| 高风险漏判率 | P0 失败被 Judge 判通过的比例 |
| 高风险误杀率 | P0 正常样本被 Judge 判失败的比例 |
| 边界稳定性 | 同一批样本重复评分的波动 |
| 规则覆盖率 | 可由确定性规则覆盖的检查项占比 |
| 人工路由率 | 进入人工复核的样本比例 |
| 数据漂移率 | 因外部事实变化失效的 Case 占比 |
| 评分器失败率 | Scorer 超时、解析失败或无效输出的比例 |

Judge 正式进入自动化流程前，建议人工一致率达到约 85%，同时重点控制 P0 漏判率。

## 8.9 线上业务效益指标

| 业务目标 | 可选指标 |
|---|---|
| 提升自助服务 | 自助解决率、转人工率、重复咨询率 |
| 提升处理效率 | 人均处理时长、工单处理时长、自动闭环率 |
| 提升用户体验 | CSAT、NPS、投诉率、负反馈率 |
| 提升业务成功 | 支付、退款、下单、审核、处置成功率 |
| 降低风险 | P0 事故数、资损金额、隐私和合规事件数 |
| 降低成本 | 单任务成本、人工替代量、成功任务成本 |

线上效益应通过灰度、A/B 或前后对照验证，不能仅由离线分数推断。

## 9. 第六步：评分公式与门禁设计

## 9.1 Case 级评分

推荐采用“Hard Gate + Soft Score”，而不是简单总分平均。

```text
HardPass = H1 ∧ H2 ∧ ... ∧ Hn

SoftScore =
    w_process × ProcessScore
  + w_output  × OutputScore
  + w_stable  × StabilityScore
  + w_cost    × EfficiencyScore
  + w_exp     × ExperienceScore

CasePass = HardPass AND SoftScore ≥ T
```

当 HardPass = 0 时，Case 直接失败，SoftScore 只用于分析，不得把 P0 风险平均掉。

## 9.2 套件级指标

```text
Suite Pass Rate = 通过 Case 数 / 有效 Case 总数
P0 Incident Rate = P0 失败 Case 数 / P0 Case 总数
Macro Score = 各场景平均分的未加权平均
Weighted Score = Σ(场景权重 × 场景得分)
```

报告中应同时提供总体指标、分场景指标、分风险指标和失败类型分布，避免高频简单样本掩盖低频高风险失败。

## 9.3 推荐发布门禁

### P0：必须满足

- 安全、隐私、资损、越权事件为 0；
- 关键幻觉和关键错误承诺为 0；
- 高风险任务路由、必要工具和关键参数正确率达到 100%；
- 不允许结果正确但过程违规的假阳性；
- 工具失败时不得编造结果。

### P1：版本门槛

- 核心场景通过率通常不低于 95%；
- 关键决策任务重点检查 pass^5 或更高重复次数；
- p95 延迟、Token 和单任务成本不得超过基线退化阈值；
- 新版本相对基线不得出现显著回归；
- 高风险分组不得被总体平均分掩盖。

### P2：趋势观察

- 清晰度、简洁度、风格和满意度不显著下降；
- 能力集通过率持续提高；
- 线上业务指标随灰度逐步改善。

## 9.4 版本比较规则

新版本接受条件建议定义为：

```text
P0 无新增失败
AND 核心指标达到绝对门槛
AND 相对基线无显著回归
AND 至少一个目标指标达到最小有效提升
AND 效率成本未超过约束
```

不应只使用“候选分数比当前高 0.1 分”作为接受依据，因为差异可能来自随机波动。

## 10. 第七步：重复实验与统计分析

## 10.1 重复运行

建议：

- 开发快速检查：N = 1；
- 常规回归：N = 3；
- 关键版本或高风险任务：N = 5–10。

不同风险类型可采用不同容忍度：

| 类型 | 容忍建议 |
|---|---|
| 关键决策、支付、合规 | N 次全部通过 |
| 辅助分析、报告生成 | 失败率通常不超过 10% |
| 创意生成 | 允许更高多样性，但核心约束必须全部满足 |

## 10.2 置信区间

二元通过率应报告置信区间，例如 Wilson 区间；连续分数、成本和延迟可使用 Bootstrap 置信区间。

## 10.3 配对版本比较

同一批 Case 比较版本 A 和 B，应采用配对分析：

- 二元通过/失败：McNemar 检验或配对 Bootstrap；
- 连续评分：配对 Bootstrap、Wilcoxon 符号秩检验；
- 延迟和成本：同时比较中位数、p95 和尾部退化；
- 多指标比较：P0 先做约束，P1 再比较收益。

## 10.4 最小有效变化

发布前预先定义最小可感知变化，例如：

- 通过率至少提升 2 个百分点；
- p95 延迟下降至少 10%；
- 成功任务成本下降至少 5%；
- P0 指标不允许任何退化。

只有超过统计噪声且达到业务意义的变化，才应影响发布决策。

## 11. 第八步：Badcase 分析与根因定位

## 11.1 Badcase 来源

- 离线评测失败；
- 线上会话和低满意度样本；
- 投诉和工单；
- 人工质检；
- 版本回归；
- 安全监控和异常告警；
- Judge 与规则冲突样本。

所有来源应汇入统一 Badcase 任务表。

## 11.2 RCA 五步法

### 第一步：证据汇总

根据 session_id、trace_id 或 run_id 汇总输入、输出、Prompt、版本、工具调用、异常、耗时和中间产物。

### 第二步：问题现象分类

先描述现象，不要提前等同于根因，例如：

- 答非所问；
- 事实性错误；
- 过度承诺；
- 缺少必要澄清；
- 工具未调用；
- 输出不完整；
- 内部信息泄漏。

### 第三步：候选模块缩圈

建立“问题现象 × 候选模块”映射：

| 问题现象 | 优先检查模块 |
|---|---|
| 答非所问 | 意图识别、Query 改写、上下文管理 |
| 事实性错误 | 检索、知识筛选、工具返回解释、生成 |
| 过度承诺 | 风险规则、Guardrail、回复生成 |
| 未澄清 | 槽位抽取、上下文判断、对话策略 |
| 关键工具未调用 | 路由、规划、Skill 核心流程 |
| 参数错误 | 参数构造、Schema 理解、类型转换 |

### 第四步：分模块诊断

对候选模块逐一标记：

- PASS：输入输出正确；
- SOFT_PASS：基本正确但存在瑕疵；
- FAIL：存在直接证据表明该模块导致失败。

### 第五步：定责和行动项

输出：

- 主责和次责模块；
- 根因大类和具体枚举；
- 关键证据；
- 影响范围；
- 修复 Owner；
- 修复动作；
- 验收用例和回归范围。

## 11.3 根因标签建议

- `route_error`
- `intent_error`
- `context_loss`
- `planning_error`
- `missing_knowledge_lookup`
- `retrieval_miss`
- `evidence_misuse`
- `wrong_tool`
- `missing_tool_call`
- `tool_order_error`
- `invalid_tool_args`
- `tool_failure_unhandled`
- `wrong_state_change`
- `unsupported_claim`
- `unsafe_internal_leak`
- `over_permission`
- `overconfident_when_uncertain`
- `bad_public_action`
- `judge_error`
- `data_drift`

## 11.4 Badcase 聚类

报告不应只是罗列 100 个失败样本，而应聚合为问题簇，例如：

```text
“已发货退款”场景共 23 条失败：
- 18 条跳过订单状态查询
- 4 条参数字段错误
- 1 条工具超时后编造结果
主要集中在 Skill v1.8 的新增分支
```

聚类维度可包括根因、场景、工具、知识点、版本和风险等级。

## 12. 第九步：借鉴 SkillOpt 做受控优化

## 12.1 SkillOpt 的核心思想

SkillOpt 将自然语言 Skill 文档视为可训练状态，冻结目标模型，通过以下循环优化：

```text
rollout
  → reflect
  → aggregate
  → select edits
  → bounded update
  → held-out validation gate
  → accept / reject
```

最终部署的是验证表现最好的 `best_skill.md`，无需在生产推理时额外调用优化器模型。

## 12.2 角色划分

- **目标模型**：执行任务，权重冻结；
- **Skill**：唯一被修改的自然语言资产；
- **Optimizer**：分析成功/失败轨迹并提出修改；
- **Train 集**：提供 rollout 和修改证据；
- **Selection 集**：决定修改是否接受；
- **Test 集**：最终报告；
- **Rejected buffer**：记录已验证无效或有害的修改。

## 12.3 Bounded Edit

每轮只允许有限数量的：

- add；
- delete；
- replace。

避免直接整篇重写，因为大范围修改会导致：

- 已有成功规则被破坏；
- 回归无法定位到具体改动；
- Skill 长度失控；
- 修改效果不可审计。

## 12.4 成功和失败轨迹都要分析

- 失败轨迹用于发现缺失规则和错误策略；
- 成功轨迹用于识别必须保留的有效行为；
- 修改建议应来自多个样本的共同模式，而不是为单条 Case 硬编码。

## 12.5 验证集门控

SkillOpt 默认接受规则是：候选 Skill 在独立 Selection 集上的分数必须严格高于当前版本。

生产实践建议扩展为：

```text
P0 不退化
AND 候选在 Selection 集超过当前版本
AND 差异超过最小有效变化或统计噪声
AND 成本与长度约束未被突破
```

## 12.6 Rejected Edit Buffer

每次被拒绝的修改应记录：

- 修改内容；
- 想解决的问题；
- 影响的 Case；
- Validation 结果；
- 失败原因；
- 下次应避免的方向。

这可以防止优化器反复提出“看起来合理但已被证明有害”的修改。

## 12.7 Validation 过拟合风险

固定 Selection 集被反复查询，会形成自适应过拟合。可采用：

- 轮换验证 Fold；
- 隐藏 Holdout；
- 限制候选查询预算；
- 定期刷新部分长尾样本；
- 最终 Test 严格隔离；
- 对微小差异使用重复执行和置信区间。

## 12.8 SkillOpt 的适用边界

SkillOpt 更适合：

- 有可靠 Scorer；
- 任务可重复执行；
- Skill 可独立版本化；
- 修改可以通过 held-out 数据验证的场景。

不应直接照搬到：

- Ground Truth 不明确；
- 高度主观且 Judge 未校准；
- 外部状态不可复现；
- 多模块同时变化、无法归因的场景。

## 13.1 推荐目录结构

```text
eval/
├── cases/
│   ├── train.jsonl
│   ├── validation.jsonl

├── rejected-edits/
├── results/
├── reports/
```

## 13.2 评测触发时机

| 变更类型 | 建议触发 |
|---|---|
| Prompt / Skill 修改 | PR 前自动回归 |
| 工具 Schema / API 修改 | 相关工具专项 + 全链路回归 |
| 模型版本升级 | 全量对比 + 稳定性评测 |
| 知识库更新 | 知识专项 + 高风险问答回归 |
| Guardrail 修改 | 安全对抗集全量运行 |
| 定期巡检 | 线上回放、数据漂移和成本趋势 |

## 13.3 执行模式

- **Smoke**：少量 P0 Case，快速检查环境和主链路；
- **Regression**：回归集全量运行；
- **Stability**：重点 Case 重复 N 次；
- **Capability**：能力集评测，用于发现可提升空间；
- **Red Team**：越权、注入、泄露和恶意输入；
- **Model Compare**：同一套 Case 横向比较多个模型；
- **Rescore**：保留原 Trace，只更新评分器重新打分。

## 13.4 报告结构

### 全局概览

- 版本信息；
- Case 数、有效 Case 数和漂移 Case 数；
- 总体通过率、P0 失败数；
- pass@k、pass^k；
- p50 / p95 延迟；
- Token、成本、工具调用；
- 相对基线变化和显著性判断。

### 分组结果

按场景、风险、Agent / Skill、工具、失败类型和业务路径分组。

### 单 Case 详情

- 输入和期望；
- 多次 Trial；
- Trace；
- 规则评分；
- Judge 评分和理由；
- 人工结论；
- 与基线差异；
- RCA 和修复建议。

### 版本四象限

| 分类 | 含义 |
|---|---|
| 稳定通过 | 旧版、新版均通过 |
| 已修复 | 旧版失败、新版通过 |
| 新增回归 | 旧版通过、新版失败 |
| 持续失败 | 旧版、新版均失败 |

新增回归应优先处理，不能被总体平均分提升掩盖。

## 14. 质量资产闭环

每条可复现 Badcase 至少可以生产以下资产：

1. 一条回归用例；
2. 一条根因标签和证据链；
3. 一项规则、Judge 标准或人工验收标准；
4. 一条 Prompt / Skill / 工具 / 知识修复动作；
5. 必要时形成训练或优化样本。

Badcase 入库应满足：

- 可复现，或有稳定 Trace 和人工确认；
- 期望行为明确；
- 根因清楚；
- 有代表性；
- 已脱敏并符合数据合规要求。

回归集不能无限膨胀：

- 同簇失败保留代表例；
- P0 / P1 高风险长期保留；
- 连续多版本稳定通过且风险低的样本可降级为抽样集；
- 新分布优先抽取低置信、高影响、新意图、新工具和新知识点样本。

最终应沉淀：

- 用例库；
- Trace 库；
- Ground Truth 库；
- Judge 校准集；
- 根因标签库；
- Rejected Edit 库；
- 修复建议库；
- 回归集和线上回放集。

---

## 15. 分阶段落地路线

## 阶段一：最小可用评测闭环

目标：先解决“是否做对”和“能否复现”。

- 明确 P0 质量契约；
- 建立 50–100 条 Golden Set；
- 打通 Agent 执行和结构化 Trace；
- 建立确定性 Scorer；
- 输出 Case 明细和 Badcase 报告。

## 阶段二：语义评分与稳定性

目标：解决“质量是否好”和“是否稳定”。

- 引入 LLM-as-Judge；
- 建立人工校准集；
- 运行 N=3/5 稳定性评测；
- 加入 Token、延迟、成本；
- 建立发布门禁。

## 阶段三：RCA 与受控优化

目标：解决“为什么错”和“修改是否真的有效”。

- 建立问题现象 × 候选模块映射；
- 结构化根因标签和 Owner；
- 区分 Train / Selection / Test；
- 引入 bounded edit、rejected buffer 和验证门控；
- 建立版本四象限和回滚机制。

## 阶段四：线上反馈与业务效益

目标：解决“离线变好是否带来线上价值”。

- 接入灰度和线上监控；
- 建立 Session 解决率、转人工率和业务成功率；
- 自动发现低置信和新分布样本；
- 形成线上 Badcase → 回归资产的持续生产线。

## 16. 常见误区

1. **只看最终答案。** 会漏掉结果假阳性和危险执行路径。
2. **用一个总分解决所有问题。** P0 风险会被平均分掩盖。
3. **所有项目共用一套权重。** 不同 Agent 类型和风险等级必须定制。
4. **能用代码判的也交给 Judge。** 增加成本和不稳定性。
5. **Judge 不校准就进门禁。** 评分器错误会被误认为 Agent 错误。
6. **只做随机线上抽样。** 高频正常样本会掩盖高风险长尾。
7. **一次运行就做版本判断。** 无法区分真实变化和随机波动。
8. **把参考轨迹当唯一正确路径。** 应允许等价路径，只约束必要步骤和禁止行为。
9. **多个模块同时修改。** 一旦回归将无法归因。
10. **不断试 Validation 集。** 会造成自适应过拟合。
11. **发现问题但不形成回归资产。** 同一问题会反复出现。
12. **离线提升就直接全量。** 必须观察线上体验和业务结果。

## 17. 最终检查清单

### 方法设计

- [ ] 已明确 Agent 类型和业务风险；
- [ ] 已定义 P0 / P1 / P2；
- [ ] 同时评测 Outcome、Output、Trace、Session 和 System；
- [ ] Case 级和套件级成功标准均明确。

### 数据集

- [ ] 覆盖触发、核心逻辑、产物质量和异常容错；
- [ ] 包含正例、负例、边界例和对抗例；
- [ ] Train、Selection、Test 和 Regression 已隔离；
- [ ] 外部状态有 Fixture 或漂移治理机制。

### 评分器

- [ ] 规则优先、Judge 补充、人工兜底；
- [ ] Judge 有分档 Rubric、理由、置信度和结构化输出；
- [ ] Judge 已用人工金标校准；
- [ ] 规则与 Judge 冲突有人工路由。

### 指标与门禁

- [ ] P0 一票否决，不被平均分覆盖；
- [ ] 同时报告 pass@k 和 pass^k；
- [ ] 报告 p95 延迟、Token 和成本；
- [ ] 报告置信区间、基线差异和最小有效变化；
- [ ] 新版本有绝对门槛、相对门槛和回滚策略。

### 优化闭环

- [ ] Badcase 能定位责任模块和 Owner；
- [ ] 修改是小步、可审计的 bounded edit；
- [ ] 候选版本由独立 Selection 集门控；
- [ ] 被拒修改进入 Rejected Edit Buffer；
- [ ] 线上 Badcase 可回流为质量资产。

## 18. 结论

完整的 Agent / Skill 评测体系，不是一套固定指标表，而是一条贯穿研发、发布和运营的质量生产线：

```text
以业务风险定义质量契约
以 Golden Set 和 Trace 建立可复现证据
以规则、Judge、人工组成分层评分体系
以 pass^k 和统计分析判断真实稳定性
以 RCA 把低分转化为责任模块和修复动作
以 bounded edit 和 held-out gate 控制 Skill 迭代
以发布门禁、灰度和线上反馈验证真实价值
```

最终衡量这套体系是否成熟，不是看它能不能生成一张漂亮的分数表，而是看它能否稳定做到三件事：

1. 在上线前发现真实风险；
2. 把失败快速转化为可执行修复；
3. 让每一轮 Agent / Skill 迭代都可比较、可解释、可回滚。
